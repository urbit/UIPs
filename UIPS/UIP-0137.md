## Abstract

This UIP defines a minimal, interoperable age-bracket signaling standard for Arvo, aligned to California AB1043. It standardizes: (1) host-side collection at setup, (2) runtime signaling into Arvo, (3) app age-rating metadata in docket manifests, and (4) OS-level handling for app download and launch decisions in both Landscape and CLI install paths. The proposal uses four required brackets: under 13, 13 to under 16, 16 to under 18, and 18 or older.

## Motivation

The statutory requirements are in [California AB1043](https://leginfo.legislature.ca.gov/faces/billTextClient.xhtml?bill_id=202520260AB1043), codified as the Digital Age Assurance Act (Civil Code Sections 1798.500-1798.505). AB1043 requires operating systems and covered app stores to provide a usable setup interface for age input and to expose age-bracket signals to developers at download and launch. Urbit currently lacks a canonical, system-level path for this signal.

Without a shared standard:

- host runtimes will implement incompatible behavior,
- app installers will not have consistent policy inputs,
- and app developers will either over-collect personal data or avoid age-gating entirely.

A minimal standard should capture the user birthday once, derive the bracket, and expose only the bracket signal to application install/launch flows.

## Specification

The key words "MUST", "MUST NOT", "REQUIRED", "SHALL", "SHALL NOT", "SHOULD", "SHOULD NOT", "RECOMMENDED", "NOT RECOMMENDED", "MAY", and "OPTIONAL" in this document are to be interpreted as described in RFC 2119 and RFC 8174.

### AB1043 Requirements

This UIP adopts the following AB1043 requirements as kernel/runtime standards:

- Account setup MUST include an accessible interface requiring an account holder to provide user birth date, age, or both for age-bracket signaling (Civil Code Section 1798.501(a)(1)).
- Runtime/provider signaling MUST support four categories: under 13, 13 to under 16, 16 to under 18, and 18 or older (Sections 1798.500(b), 1798.501(a)(2)).
- Developer-facing app workflows MUST request and use the signal at download and launch (Section 1798.501(b)(1)).
- Implementations MUST send only the minimum information necessary and MUST NOT share signal data for unrelated purposes (Sections 1798.501(a)(3), 1798.501(b)(4)).
- Signal handling across first-party and third-party apps MUST be non-discriminatory (Section 1798.504(c)).
- Implementations SHOULD plan migration behavior for existing devices/apps consistent with AB1043's operative dates (January 1, 2027 and July 1, 2027; Section 1798.502).

### 1. Bracket Model

An implementation compliant with this UIP MUST support exactly these four age brackets:

- under 13 (`lt13`)
- at least 13 and under 16 (`lt16`)
- at least 16 and under 18 (`lt18`)
- at least 18 (`gt18`)

### 2. Setup and Input Requirements

An Urbit host runtime MUST provide an accessible interface during setup to collect age input as birthday, age, or both.

If birthday is collected, the runtime MUST derive the bracket from local current date.

For command-line `vere`, this UIP specifies:

- `--age-check [YYYY-MM-DD]` as the input surface,
- interactive prompt when no value is provided and terminal interaction is enabled,
- non-interactive failure when `-t/--no-tty` or `-d/--daemon` is set and no birthday value is provided.

### 3. Runtime-to-Arvo Signal Injection

The runtime MUST pass the age result into Arvo via a `%what` card on wire `[/arvo ~]`.

This proposal standardizes the namespace binding:

- path: `/meta/ca.ab1043`
- mark: `%noun`
- payload: `[mode birthday]`

Where:

- `mode` is `%boot` when signal is injected as part of initial ship creation and `%pier` when injected on resume,
- `birthday` is a normalized `YYYY-MM-DD` text value.

Arvo MUST store the birthday and derive the bracket dynamically from the stored birthday and current time (`now.bowl`) on each query. The bracket codes are `1=lt13`, `2=lt16`, `3=lt18`, `4=gt18`. App install/launch policy paths SHOULD consume bracket-level signal data and SHOULD NOT require additional personal data beyond what is needed for policy.

### 4. Boot and Resume Semantics

Both new-ship boot and existing-pier resume MUST accept `--age-check`.

For new ship boot, implementations SHOULD inject age metadata as part of boot sequence enhancements (for example, via `%prop` hind events).

For existing pier resume, implementations SHOULD inject the metadata as a one-shot runtime ovum after I/O driver initialization.

### 5. App Installation and Launch Standard

For purposes of AB1043-style handling in Urbit OS surfaces:

- an app installation surface (CLI, web UI, or app store front-end) MUST request and apply the Arvo age-bracket signal before completing app download/install,
- an app launch surface MUST request and apply the age-bracket signal at launch,
- first-party and third-party apps MUST be treated in a non-discriminatory manner by the same signal policy,
- only the minimum data required for policy (the bracket) SHOULD be exposed to app-facing policy decisions.

This UIP standardizes signal transport and timing. It does not prescribe one universal content policy (for example, allow/deny lists by category), which MAY be defined by separate UIPs or jurisdictional policy desks.

### 6. App Metadata in Docket Manifest

Installable apps distributed through docket MUST provide age-rating metadata in docket manifest data.

This UIP standardizes a new docket metadata field:

- key: `age-rating`
- values: `all`, `13+`, `16+`, `18+`, `unrated`

`age-rating` represents the app's declared minimum audience bracket for install/launch decisions:

- `all`: no age restriction
- `13+`: user MUST be at least in the 13-to-under-16 bracket
- `16+`: user MUST be at least in the 16-to-under-18 bracket
- `18+`: user MUST be in the 18-or-older bracket
- `unrated`: no declared app rating (transitional/legacy)

Legacy dockets without `age-rating` MUST be treated as `unrated`.

For typed Hoon schemas, this UIP RECOMMENDS the internal tag mapping:

- `all` -> `%all`
- `13+` -> `%gt13`
- `16+` -> `%gt16`
- `18+` -> `%gt18`
- `unrated` -> `%unrated`

Non-docket install flows SHOULD provide equivalent app age-rating metadata. If unavailable, they SHOULD be treated as `unrated`.

### 7. Installer Integration: Landscape and CLI

The OS-level install and launch paths in Arvo SHOULD be centralized so policy is consistent across interfaces.

- Landscape installs and launches MUST consult the same Arvo age signal derived from `/meta/ca.ab1043`.
- CLI installs and launches MUST consult that same Arvo age signal.
- Landscape and CLI MUST share one policy decision procedure over `[user-age-signal app-age-rating]` so results do not differ by interface.
- If no signal is available, both interfaces MUST follow the same fallback policy.

## Rationale

The design is intentionally minimal:

- one canonical kernel path,
- one normalized payload shape,
- one bracket mapping,
- and explicit boot/resume behavior.

Using `%what` avoids introducing a new Arvo card type while keeping data accessible from userspace. Separating setup/input from app-policy logic also lets implementations satisfy legal signaling obligations without forcing a single global moderation regime.

## Backwards Compatibility

This UIP is additive.

Ships without `/meta/ca.ab1043` remain valid and continue existing behavior. Install/launch surfaces that adopt this UIP SHOULD treat missing data as "no signal" and follow local fallback policy.

Existing docket manifests without `age-rating` remain valid and MUST be interpreted as `unrated` until upgraded.

## Reference Implementation

A prototype implementation exists in `vere` and demonstrates:

- `--age-check` birthday input and interactive fallback,
- birthday injection via `%prop` from runtime into Arvo at boot,
- birthday injection as one-shot event on pier resume,
- canonical write to `/meta/ca.ab1043` via `%what`,
- dynamic bracket derivation from stored birthday and current time.

### Reference Implementation Sketch

The following sketch shows the intended schema and policy integration points.

#### 1. `pkg/landscape/sur/docket.hoon`

```hoon
+$  age-rating
  $?  %all
      %gt13
      %gt16
      %gt18
      %unrated
  ==

+$  clause
  $%  ...
      [%age-rating rating=age-rating]
  ==

+$  docket
  $:  %1
      title=@t
      info=@t
      color=@ux
      =href
      image=(unit url)
      =version
      website=url
      license=cord
      rating=age-rating
  ==
```

#### 2. `pkg/landscape/lib/docket.hoon`

```hoon
|%
++  mime
  |%
  +$  draft
    $:  ...
        age-rating=(unit age-rating)
    ==

  ++  finalize
    |=  =draft
    ^-  (unit docket)
    ...
    =/  rating=age-rating  ?~(age-rating.draft %unrated u.age-rating.draft)
    :*  %1
        u.title
        u.info
        u.color
        u.href
        image
        u.version
        u.website
        u.license
        rating
    ==

  ++  from-clauses
    =|  =draft
    |=  cls=(list clause)
    ^-  (unit docket)
    ...
      %age-rating  draft(age-rating `rating.clause)
    ...

  ++  to-clauses
    |=  d=docket
    ^-  (list clause)
    ...
      age-rating+rating.d
    ...
```

#### 3. Bracket derivation gate

```hoon
|%
++  parse-dob
  |=  dob=@t
  ^-  @da
  =/  t  (trip dob)
  =/  y  (slav %ud (crip (scag 4 t)))
  =/  m  (slav %ud (crip (scag 2 (slag 5 t))))
  =/  d  (slav %ud (crip (scag 2 (slag 8 t))))
  (year [[& y] m d 0 0 0 ~])
::
++  bracket
  |=  [dob=@t now=@da]
  ^-  ?(%lt13 %lt16 %lt18 %gt18)
  =/  birth  (yore (parse-dob dob))
  =/  today  (yore now)
  =/  age=@ud
    =/  base  (sub y.today y.birth)
    ?:  ?|  (lth m.today m.birth)
            ?&  =(m.today m.birth)
                (lth d.t.today d.t.birth)
            ==
        ==
      (dec base)
    base
  ?:  (lth age 13)  %lt13
  ?:  (lth age 16)  %lt16
  ?:  (lth age 18)  %lt18
  %gt18
--
```

#### 4. Shared install/launch policy gate (Arvo, used by Landscape + CLI)

```hoon
|%
++  allow-by-age
  |=  [dob=(unit @t) now=@da app=age-rating]
  ^-  ?
  ?~  dob
    ?|  ?=(%all app)
        ?=(%unrated app)
    ==
  =/  user  (bracket u.dob now)
  ?-  app
    %all      &
    %unrated  &
    %gt13     ?|  =(user %lt16) =(user %lt18) =(user %gt18)  ==
    %gt16     ?|  =(user %lt18) =(user %gt18)  ==
    %gt18     =(user %gt18)
  ==
```

Landscape install/launch and CLI install/launch SHOULD both call this same gate with:

- stored birthday from `/meta/ca.ab1043` (runtime-provided signal),
- current time from `now.bowl`,
- app rating from docket (or `unrated` fallback).

## Security Considerations

The signal pipeline carries age-related metadata and therefore MUST minimize data sharing.

Implementations SHOULD:

- avoid exposing raw birthday outside kernel/runtime internals where possible,
- expose bracket-level data to app policy paths,
- avoid sharing signal data with unrelated third parties,
- apply the same policy pipeline to first-party and third-party apps.

App-provided `age-rating` metadata is declarative and MAY be inaccurate. Implementations SHOULD treat it as policy input, not identity proof, and SHOULD support auditing/override mechanisms for obviously incorrect app ratings.

Dynamic bracket derivation from stored birthday eliminates stale-bracket risk. Runtimes SHOULD support re-collection workflows for correcting an incorrect birthday.
